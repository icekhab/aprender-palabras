# Общая техническая документация

## 1. Назначение

Этот документ фиксирует общий стек, структуру проекта и способ локального запуска `aprender-palabras`.

Подробная техническая документация для базы данных, API, экранов и алгоритмов будет создаваться отдельно перед реализацией каждой функции. Продуктовое поведение описано в [продуктовых требованиях](../product/README.md).

## 2. Общая архитектура

Приложение состоит из трёх частей:

1. React PWA — пользовательский интерфейс.
2. Node.js API — бизнес-логика и работа с внешними сервисами.
3. PostgreSQL — постоянное хранение пользователей, карточек, уроков и прогресса.

Frontend не обращается к базе данных, OpenAI и Unsplash напрямую. Все такие запросы проходят через backend.

```text
React PWA → NestJS API → PostgreSQL
                     ├→ OpenAI
                     └→ Unsplash
```

Для первой версии используется модульный монолит: один frontend, один backend и одна база данных. Микросервисы, Redis и очереди сообщений пока не нужны.

## 3. Технологии

### Общие

| Технология | Назначение |
|---|---|
| TypeScript | единый язык frontend и backend |
| Node.js LTS | среда выполнения |
| pnpm | зависимости и monorepo |
| ESLint + Prettier | проверка и форматирование кода |
| Vitest | unit и integration тесты |
| Playwright | браузерные E2E-тесты |

Точные версии фиксируются в `package.json` и `pnpm-lock.yaml` при создании проекта. Используются только стабильные версии, без beta и release candidate.

### Frontend

| Технология | Назначение |
|---|---|
| React | пользовательский интерфейс |
| Vite | сборка и локальный dev server |
| `vite-plugin-pwa` | manifest, service worker и установка PWA |
| React Router | маршрутизация |
| TanStack Query | запросы к API и server state |
| React Hook Form | формы |
| Zod | проверка форм и входных параметров API |
| Web Speech API | воспроизведение испанского текста на устройстве |

Интерфейс разрабатывается mobile-first, но должен полноценно работать на компьютере.

### Backend

| Технология | Назначение |
|---|---|
| NestJS | структура Node.js API |
| REST JSON | взаимодействие frontend и backend |
| Prisma ORM | запросы к БД и миграции |
| PostgreSQL | основная база данных |
| Argon2id | хеширование паролей |

Backend отвечает за авторизацию, доступ только к собственным данным пользователя, бизнес-правила и интеграции.

Frontend и backend проверяют формы и входные параметры общими Zod-схемами. Ответы API не проходят runtime-проверку: frontend считает их соответствующими общим TypeScript-типам.

### Внешние сервисы

| Сервис | Использование |
|---|---|
| OpenAI, модель `gpt-6-luna` | варианты перевода и генерация содержимого карточки |
| Unsplash API | поиск изображений по URL с обязательной атрибуцией |
| Web Speech API | синтез речи без создания аудиофайлов |

API-ключи OpenAI и Unsplash хранятся только на backend в переменных окружения.

## 4. Размещение

Для личного тестирования:

| Компонент | Платформа |
|---|---|
| React PWA | Vercel Hobby |
| NestJS API | Railway Hobby |
| PostgreSQL | Railway |

Frontend обращается к относительному пути `/api`. В production Vercel перенаправляет эти запросы в Railway. Это позволяет браузеру работать с приложением как с одним сайтом.

Ожидаемая стоимость тестовой версии — примерно `$5–18` в месяц без учёта домена, налогов и заметной пользовательской нагрузки.

## 5. Структура репозитория

Планируемая структура monorepo:

```text
/
├── apps/
│   ├── web/                  # React PWA
│   │   ├── src/
│   │   │   ├── app/         # router, providers, layouts
│   │   │   ├── pages/       # страницы
│   │   │   ├── features/    # функции продукта
│   │   │   └── shared/      # UI, API client, utilities
│   │   └── public/
│   └── api/                  # NestJS API
│       ├── src/
│       │   ├── auth/
│       │   ├── cards/
│       │   ├── lessons/
│       │   ├── training/
│       │   └── integrations/
│       └── prisma/
│           ├── schema.prisma
│           └── migrations/
├── packages/
│   ├── contracts/            # Zod-схемы входных данных и TypeScript-типы ответов
│   ├── domain/               # общие чистые бизнес-функции
│   ├── eslint-config/
│   └── tsconfig/
├── docs/
│   ├── product/
│   └── technical/
├── compose.yaml
├── package.json
├── pnpm-workspace.yaml
└── pnpm-lock.yaml
```

Документация функции будет находиться рядом с общими техническими документами и создаваться непосредственно перед разработкой этой функции.

## 6. Локальная разработка

### 6.1. Необходимые инструменты

- Node.js LTS;
- Corepack и pnpm;
- Docker Desktop;
- Git.

PostgreSQL запускается в Docker. Frontend и backend запускаются локальными Node.js-процессами для удобной перезагрузки кода.

### 6.2. Локальные адреса

| Компонент | Адрес |
|---|---|
| Frontend | `http://localhost:5173` |
| Backend | `http://localhost:3000` |
| PostgreSQL | `localhost:5432` |

Vite перенаправляет локальные запросы `/api` на `http://localhost:3000`.

### 6.3. Переменные окружения

В репозитории хранится `.env.example` без секретов. Разработчик создаёт локальные файлы `.env`, которые игнорируются Git.

Минимальные переменные backend:

```dotenv
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/aprender_palabras
OPENAI_API_KEY=
OPENAI_MODEL=gpt-6-luna
UNSPLASH_ACCESS_KEY=
APP_ORIGIN=http://localhost:5173
```

Приложение должно запускаться без ключей OpenAI и Unsplash, но соответствующие функции будут недоступны. Сохранение карточки вручную должно продолжать работать.

### 6.4. Команды

После создания каркаса проекта используются единые команды из корня:

```bash
corepack enable
pnpm install
docker compose up -d postgres
pnpm db:migrate
pnpm dev
```

`pnpm dev` одновременно запускает frontend и backend.

Дополнительные команды:

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm test:e2e
pnpm format
pnpm db:studio
docker compose down
```

Ожидаемое назначение:

| Команда | Результат |
|---|---|
| `pnpm db:migrate` | применить локальные Prisma-миграции |
| `pnpm dev` | запустить `web` и `api` в watch mode |
| `pnpm lint` | проверить правила кода |
| `pnpm typecheck` | проверить TypeScript без сборки |
| `pnpm test` | выполнить unit/integration тесты |
| `pnpm test:e2e` | выполнить Playwright-тесты |

Эти scripts должны быть добавлены при создании каркаса приложения; сейчас документ фиксирует их будущий контракт.

## 7. Порядок дальнейшей работы

Перед началом каждой функции:

1. выбрать соответствующий продуктовый документ;
2. описать только необходимые для функции данные, API, экраны и алгоритмы;
3. согласовать техническое решение;
4. реализовать функцию и тесты;
5. обновить документацию, если реализация потребовала изменения решения.

Рекомендуемая последовательность функций:

1. каркас проекта и авторизация;
2. карточки слов;
3. уроки;
4. прогресс и ежедневные подборки;
5. тренажёр;
6. PWA и production deployment.
